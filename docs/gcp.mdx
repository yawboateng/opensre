title: "Google Cloud"
description: "Connect Google Cloud so OpenSRE can read logs, metrics, audit trails, GKE clusters, VMs, Cloud Run, Cloud SQL, Pub/Sub and Error Reporting during investigations, across one or many projects"
---

OpenSRE reads Cloud Logging entries, Cloud Monitoring time series, Cloud Audit Logs, GKE clusters, Compute Engine VMs, Cloud Run services, Cloud SQL instances, Pub/Sub backlogs and Error Reporting groups from your Google Cloud projects — including GKE container logs and cluster metrics when no kubeconfig is registered.

This is separate from running the agent's LLM on Vertex AI. `VERTEX_AI_PROJECT` selects the model; `GCP_PROJECT_ID` selects the infrastructure being investigated. Set both if they are different projects.

## Prerequisites

- A Google Cloud project with the **Cloud Logging API**, **Cloud Monitoring API**, and **Cloud Resource Manager API** enabled
- A principal with `roles/logging.viewer` and `roles/monitoring.viewer` on each project you want to query
- Network access from the OpenSRE environment to `logging.googleapis.com`, `monitoring.googleapis.com` and `cloudresourcemanager.googleapis.com`

Everything else is opt-in, one service at a time. Enable the API and grant the role only for the tools you want:

| Tool | API to enable | Role to grant | Endpoint to reach |
| --- | --- | --- | --- |
| `gcp_list_gke_clusters` | Kubernetes Engine | `roles/container.viewer` | `container.googleapis.com` |
| `gcp_list_compute_instances` | Compute Engine | `roles/compute.viewer` | `compute.googleapis.com` |
| `gcp_list_cloud_run_services` | Cloud Run Admin | `roles/run.viewer` | `run.googleapis.com` |
| `gcp_list_cloud_sql_instances` | Cloud SQL Admin | `roles/cloudsql.viewer` | `sqladmin.googleapis.com` |
| `gcp_pubsub_backlog` | Cloud Pub/Sub | `roles/pubsub.viewer` **and** `roles/monitoring.viewer` | `pubsub.googleapis.com` |
| `gcp_error_reporting_top_errors` | Error Reporting | `roles/errorreporting.viewer` | `clouderrorreporting.googleapis.com` |

A missing API or role disables the tool that needs it; it does not break the rest. On a multi-project query, a project that denies one call is reported in `partial_errors` and the projects that answered are still returned.

## Setup

The wizard walks through the three auth paths below and verifies the result:

```bash
opensre integrations setup gcp
```

To configure it by hand, set the environment variables directly.

### Option 1: Application Default Credentials (no configuration)

On GKE with Workload Identity, on a GCE VM, or on a laptop where you have run `gcloud auth application-default login`, OpenSRE picks up the ambient credential. Set the project and nothing else:

```bash
GCP_PROJECT_ID=my-project
```

<Note>
On GKE, the Kubernetes service account must carry the `iam.gke.io/gcp-service-account` annotation pointing at your Google service account. Without it the pod silently falls back to the node's `default` compute identity and every call fails with a 403 — and changing the annotation does **not** restart pods, so run `kubectl rollout restart deploy/<name>` afterwards.
</Note>

### Option 2: Service account key

```bash
GCP_PROJECT_ID=my-project
GCP_SERVICE_ACCOUNT_KEY=/secrets/opensre-gcp.json
```

`GCP_SERVICE_ACCOUNT_KEY` accepts either a path to the JSON file or the JSON document itself, so it works with both mounted secrets and secret-manager env injection.

### Option 3: Impersonation

Keep the ambient credential and impersonate a service account that has the read roles. This reaches other estates without minting long-lived JSON keys:

```bash
GCP_PROJECT_ID=my-project
GCP_IMPERSONATE_SERVICE_ACCOUNT=opensre-reader@my-project.iam.gserviceaccount.com
```

The ambient principal needs `roles/iam.serviceAccountTokenCreator` on the target service account.

### Environment variables

| Variable | Default | Description |
| --- | --- | --- |
| `GCP_PROJECT_ID` | — | **Required.** Default project every tool call targets. `GOOGLE_CLOUD_PROJECT` is honoured as a fallback |
| `GCP_ADDITIONAL_PROJECTS` | — | Comma-separated extra projects reachable with the **same** credential |
| `GCP_SERVICE_ACCOUNT_KEY` | — | Service-account JSON, or a path to it. Leave empty to use Application Default Credentials |
| `GCP_IMPERSONATE_SERVICE_ACCOUNT` | — | Service account to impersonate on top of the ambient credential |
| `GCP_MAX_RESULTS` | `100` | Default page size for log and metric queries (clamped to `1`–`1000`) |
| `GCP_INSTANCES` | — | JSON array registering several GCP estates, each with its own credential. See [Multiple projects](#multiple-projects) |

## Multiple projects

There are two different situations, and they are configured differently.

### One credential, many projects

IAM inherits down the resource hierarchy, so a service account granted a viewer role at the **folder or organization** level already reads every project beneath it. List those projects and OpenSRE will query across them:

```bash
GCP_PROJECT_ID=acme-prod
GCP_ADDITIONAL_PROJECTS=acme-staging,acme-data,acme-shared
```

The agent then passes `project="acme-staging"` on a tool call, `project="acme-data,acme-shared"` for several, or `project="*"` for all of them. Omitting `project` uses `GCP_PROJECT_ID`.

Cloud Logging queries all of them in **one** request, so `project="*"` is the cheap way to trace a request id across an estate.

### Many credentials

When the projects do not share a folder — separate organizations, or a key per environment — register one instance per credential:

```bash
GCP_INSTANCES='[
  {"name":"prod","tags":{"env":"prod"},"project_id":"acme-prod","additional_projects":"acme-shared"},
  {"name":"research","project_id":"acme-research","impersonate_service_account":"ro@acme-research.iam.gserviceaccount.com"}
]'
```

Every instance's projects join one flat list, so the agent still picks a **project**, never a credential — OpenSRE maps each project back to the credential that can reach it. The first instance's project is the default.

<Warning>
A project must be named in `GCP_PROJECT_ID`, `GCP_ADDITIONAL_PROJECTS`, or `GCP_INSTANCES` before a tool will query it. `gcp_list_projects` will happily *show* projects your credential can see at the org level, but querying one requires an operator to add it — this keeps a hallucinated project id from turning into an opaque 403.
</Warning>

## Investigation tools

### `gcp_logging_query`

Runs a [Cloud Logging filter](https://cloud.google.com/logging/docs/view/logging-query-language) and returns flattened entries — timestamp, severity, message, and the GKE cluster/namespace/pod/container labels when present.

- **`filter`** — the filter expression. Leave the time window out of it; OpenSRE always applies its own bound
- **`project`** — one project, a comma-separated list, or `*`. Defaults to `GCP_PROJECT_ID`
- **`severity`** — minimum severity (`DEBUG` through `EMERGENCY`)
- **`hours`** — lookback window, default `1`, capped at 30 days
- **`limit`** — page size, default `GCP_MAX_RESULTS`

The message is read from whichever payload field the producer used — `textPayload` for GKE stdout, `jsonPayload` for structured logs, `protoPayload` for Cloud Audit Logs — so audit entries are not returned blank.

### `gcp_monitoring_query`

Reads Cloud Monitoring time series for **one** project per call (unlike logging, the Monitoring API is scoped to a single project).

- **`filter`** — must name a metric type, e.g. `metric.type="kubernetes.io/container/memory/used_bytes"`
- **`project`** — a single project id
- **`hours`** — lookback window, default `1`
- **`alignment_period_seconds`** — downsampling bucket, default `300`
- **`aligner`** — optional override, e.g. `ALIGN_MAX`

By default the aligner is chosen from the metric's kind: **mean** for gauges, **per-second rate** for counters. Cloud Monitoring rejects a mean over a cumulative metric outright, so a fixed aligner would fail on most counters. The aligner actually used is returned in the result — read rate values as per second, not as raw counts.

### `gcp_audit_log_query`

Answers *who changed what, and when* — the Cloud Audit Logs equivalent of reading CloudTrail. You give it named arguments, not a filter expression; it builds the query.

- **`log_type`** — `activity` (admin writes, the default), `data_access`, `system_event`, `policy`, or `all`
- **`project`** — one project, a comma-separated list, or `*`
- **`principal`** — who acted, e.g. an email or service-account name (substring match)
- **`method`** — the API method, e.g. `compute.instances.delete` or just `delete`
- **`service`** — e.g. `compute.googleapis.com`
- **`resource`** — the target resource name, e.g. a cluster or instance name
- **`failed_only`** — only denied or errored calls
- **`hours`** — lookback window, default `24`, capped at 30 days
- **`limit`** — page size, default `GCP_MAX_RESULTS`

Each result is one record: principal, method, service, resource, caller IP, user agent, and whether it succeeded. A denied call also lists the exact IAM permission that was missing, which usually turns "the deploy failed" into a one-line fix.

<Note>
**Data Access logs are off by default in GCP.** An empty `data_access` result almost always means nobody enabled the log type, not that nobody read anything. Admin writes — the changes that cause incidents — are in `activity`, which is always on.
</Note>

You can run the same query through `gcp_logging_query`, but only if you already know audit entries live under `logName:cloudaudit.googleapis.com` and that the interesting fields hang off `protoPayload`. Get either wrong and you get zero rows with no hint why.

### `gcp_list_gke_clusters`

Lists GKE clusters across the configured projects, in every region and zone, with control-plane status, master and node versions, node counts, node pools and autoscaling ranges.

- **`project`** — one project, a comma-separated list, or `*`

Each cluster reports **`registered_as`** when a kubeconfig for it is registered with the [Kubernetes integration](/kubernetes) — that value is the name to pass as the `cluster` argument to `kubernetes_list_pods` and friends. Clusters without one are listed under `unregistered_clusters`: they are visible, but only through Cloud Logging and Monitoring until someone registers a kubeconfig. [One command registers them all](#registering-your-gke-clusters-automatically).

Matching is exact — either the registered kubeconfig `context` equals the one `gcloud container clusters get-credentials` writes (`gke_<project>_<location>_<cluster>`), or the registered instance name equals the cluster name. Nothing is matched by prefix, because two clusters called `prod` in different projects are ordinary.

`healthy` is `true` only for a `RUNNING` cluster with no conditions. A cluster can be `RUNNING` and still be reporting exhausted quota or a stuck upgrade, so read `conditions` rather than `status` alone.

### `gcp_list_compute_instances`

Lists Compute Engine VMs across the configured projects, covering every zone in one call per project.

- **`project`** — one project, a comma-separated list, or `*`
- **`status`** — e.g. `RUNNING` or `TERMINATED` (filtered server-side)
- **`name_contains`** — substring of the instance name
- **`limit`** — page size, default `100`, capped at `500`

Returns name, zone, machine type, status, creation time, internal and external IP, labels and network tags. GKE nodes additionally report `gke_cluster` and `gke_node_pool`, so a VM named in an alert can be traced back to the cluster it belongs to. Preemptible and Spot VMs are flagged — their disappearance is expected behaviour, not an incident.

`TERMINATED` means *stopped*, not deleted. A deleted instance is simply absent.

### `gcp_list_cloud_run_services`

Lists Cloud Run services across the configured projects, covering every region in one call per project.

- **`project`** — one project, a comma-separated list, or `*`
- **`name_contains`** — substring of the service name
- **`unhealthy_only`** — only services that are not `Ready` or whose latest revision never took traffic
- **`limit`** — page size, default `100`, capped at `500`

Returns readiness, the revision actually serving traffic, the container images it runs, the live traffic split, ingress setting, scaling bounds, who deployed last and any failing condition.

<Note>
**A Cloud Run deploy that changed nothing looks healthy.** When a new revision never becomes ready, Cloud Run keeps serving the previous one and the service still reports `Ready`. That shows up here as `latest_created_revision` ≠ `latest_ready_revision`, flagged as `rollout_pending`. Read `failing_conditions` on those services — that is where the pull error, crash-on-start or missing secret is named.
</Note>

Do not pass a region: the tool already queries all of them.

### `gcp_list_cloud_sql_instances`

Lists Cloud SQL database instances across the configured projects, covering every region in one call per project.

- **`project`** — one project, a comma-separated list, or `*`
- **`state`** — e.g. `RUNNABLE`, `SUSPENDED`, `MAINTENANCE`, `FAILED` (filtered server-side)
- **`name_contains`** — substring of the instance name
- **`unhealthy_only`** — only instances that are not `RUNNABLE` or are near their disk limit
- **`limit`** — page size, default `100`, capped at `500`

Returns state, database version, region and zone, tier, availability type, disk usage, replica topology, connection name, whether backups are on, scheduled maintenance and suspension reasons.

`healthy` is `true` only for a `RUNNABLE` instance that is not near its disk limit. **An instance that fills its disk stops accepting writes and still reports `RUNNABLE`**, so `state` alone will not show it — instances above 85% of provisioned disk are flagged `disk_pressure`.

`accepts_writes` is `false` on a read replica, and `replica_of` names the primary. That pair answers "why are writes failing but reads fine" without a round trip. `availability_type: ZONAL` means there is no standby, so a zone outage is an outage rather than a failover.

### `gcp_pubsub_backlog`

Lists Pub/Sub subscriptions with their current backlog, joining the subscription configuration to the two Cloud Monitoring metrics that say whether consumers are keeping up.

- **`project`** — one project, a comma-separated list, or `*`
- **`name_contains`** — substring of the subscription name **or** its topic
- **`backlogged_only`** — only subscriptions with undelivered messages or a stalled oldest message
- **`limit`** — page size, default `100`, capped at `500`

Returns `undelivered_messages` and `oldest_unacked_age_seconds` alongside the topic, delivery mode, push endpoint, ack deadline, retry backoff and dead-letter policy. Results are sorted deepest backlog first.

`oldest_unacked_age_seconds` is the field to read, not the count. A batch subscription can sit thousands deep by design; a *rising age* means consumers stopped. Anything over five minutes is flagged `stalled`.

Two subscription details explain most backlogs that will not drain on their own: a **push** subscription whose endpoint is 5xx-ing has no consumer to inspect, and a subscription with an empty `dead_letter_topic` retries a poison message forever.

<Note>
This tool needs **two** roles. With `roles/pubsub.viewer` but not `roles/monitoring.viewer`, the configuration is still returned and every subscription is marked `backlog_unknown` — deliberately, so an unreadable metric never renders as a healthy zero.
</Note>

### `gcp_error_reporting_top_errors`

Lists the top error groups from Error Reporting, already deduplicated server-side. The shortest path from "something is wrong" to a stack trace.

- **`project`** — one project, a comma-separated list, or `*`
- **`period`** — `1h` (default), `6h`, `1d`, `1w`, or `30d`
- **`order`** — `count` (default), `last_seen`, `first_seen`, or `affected_users`
- **`service`** — only groups raised by this service name
- **`limit`** — groups returned, default `20`, capped at `100`

Each group carries its count, users affected, when it was first and last seen, the service and version that raised it, and a representative stack trace truncated to its leading frames.

**`first_seen` is what makes this worth a tool call.** A group first seen twenty minutes ago is a regression; a group first seen eight months ago is background noise with the same count. Use `order="first_seen"` to surface groups that appeared during the incident.

An empty result does not mean nothing is failing. Error Reporting only sees exceptions that reach it — a service logging errors as plain text without a stack trace reports nothing here. Fall back to `gcp_logging_query` with `severity=ERROR`.

### `gcp_list_projects`

Lists the projects the agent may target. Returns the configured set, plus anything a live Resource Manager listing turns up when the credential has folder- or org-level visibility. A missing `resourcemanager.projects.list` permission is not an error — the configured set is still returned.

## Registering your GKE clusters automatically

Anything `gcp_list_gke_clusters` reports under `unregistered_clusters` is visible but unreachable — the `kubernetes_*` tools cannot run against it. One command fixes every one of them:

```bash
opensre integrations add-gke-clusters --project '*'
```

This discovers the clusters, generates a kubeconfig for each, and registers it under the [Kubernetes integration](/kubernetes), so `kubernetes_list_pods` and friends can target it by name. Re-running is safe — clusters already registered are skipped.

**Requires [`gke-gcloud-auth-plugin`](https://cloud.google.com/kubernetes-engine/docs/how-to/cluster-access-for-kubectl) on PATH.** The OpenSRE container image ships with it, so this applies to workstation installs only:

```bash
gcloud components install gke-gcloud-auth-plugin
```

The generated kubeconfig **stores no credentials**. It holds the cluster endpoint, the cluster's public CA certificate, and an instruction to ask the plugin for a token at connection time.

<Warning>
The plugin authenticates as *its own* Application Default Credentials — on a workstation, whoever ran `gcloud auth login`, which is not necessarily the identity OpenSRE used to find the cluster. When `GCP_SERVICE_ACCOUNT_KEY` is a **file path**, the generated kubeconfig pins the plugin to that same file, so both sides match. When it is inline JSON there is nothing to pin, so set `GOOGLE_APPLICATION_CREDENTIALS` yourself.
</Warning>

| Option | What it does |
|---|---|
| `--project` | One project, a comma-separated list, or `*`. Omit for the default project. |
| `--dry-run` | Report what would be registered; write nothing. |
| `--tag KEY=VALUE` | Attach a tag to every cluster registered. Repeatable. |
| `--overwrite` | Replace an existing instance whose name matches but points at another cluster. |
| `--no-verify` | Skip the connectivity probe before saving. |

Each cluster is registered under its own name and tagged `source=gke` plus its project and location. Two clusters sharing a name across projects both become `<cluster>-<project>`, so neither is ambiguous.

If the endpoint and CA certificate come back empty, grant the principal `roles/container.clusterViewer` on top of `roles/container.viewer` — that is the permission that exposes them.

<Note>
Clusters with a **private endpoint only** are reachable from inside their VPC. Run the command from a host with VPC access, or use `--no-verify` to register them for later.
</Note>

Deploying in a container, where the local store is ephemeral? Declare the clusters in `KUBERNETES_INSTANCES` instead — see [Kubernetes](/kubernetes). `--dry-run` prints the names and contexts you need.

## Verify

```bash
opensre integrations verify gcp
```

Expected output:

```
SERVICE │ SOURCE    │ STATUS   │ DETAIL
gcp     │ local env │ ✓ passed │ Connected to GCP project acme-prod (acme-prod) via ADC; scope covers 4 projects.
```

This makes a real API call, so it catches the case that a shape check cannot: credentials that resolve to the *wrong* principal.

## Example queries

GKE container errors in a namespace:

```
resource.type="k8s_container" AND resource.labels.namespace_name="payments" AND severity>=ERROR
```

Everything touching one request, across every configured project (`project="*"`):

```
trace="projects/acme-prod/traces/0123456789abcdef0123456789abcdef"
```

Who changed an IAM policy before the incident — use `gcp_audit_log_query` with `method="SetIamPolicy"` rather than writing this by hand, but the equivalent raw filter is:

```
logName:"cloudaudit.googleapis.com%2Factivity" AND protoPayload.methodName="SetIamPolicy"
```

Container memory for a workload:

```
metric.type="kubernetes.io/container/memory/used_bytes" AND resource.labels.namespace_name="payments"
```

## Troubleshooting

| Symptom | Fix |
| --- | --- |
| **403 `IAM_PERMISSION_DENIED`** | The credential resolved but lacks the role. Run `opensre integrations verify gcp` to see which principal is actually in use — on GKE this is usually the node's `default` compute identity, meaning the Workload Identity annotation is missing or the pod predates it. |
| **`unknown GCP project(s): …`** | The project is not in `GCP_PROJECT_ID`, `GCP_ADDITIONAL_PROJECTS`, or `GCP_INSTANCES`. Add it and restart. |
| **`The aligner cannot be applied to metrics with kind CUMULATIVE`** | Only happens with an explicit `aligner`. Drop it and let OpenSRE pick, or use `ALIGN_RATE`. |
| **Empty log results** | Cloud Logging filters are exact-match by default. Confirm the same filter returns rows in **Logs Explorer** over the same window, and remember the window comes from `hours`, not from a `timestamp` clause in the filter. |
| **Nothing from `gcp_list_projects` beyond what you configured** | The credential lacks `resourcemanager.projects.list`. Harmless — configured projects still work. |
| **`gcp_audit_log_query` returns nothing for `data_access`** | Data Access audit logs are disabled by default. Enable them per service in **IAM & Admin → Audit Logs**, or query `activity` instead. |
| **A GKE cluster is listed but has no `registered_as`** | No kubeconfig is registered for it, so the `kubernetes_*` tools cannot reach it. Run `opensre integrations add-gke-clusters --project '*'`, or investigate it through Cloud Logging and Monitoring. |
| **`add-gke-clusters` says the plugin is not on PATH** | Install it with `gcloud components install gke-gcloud-auth-plugin`. Without it the generated kubeconfig cannot obtain a token, so the command refuses to write one. The container image already includes the plugin, so seeing this in a pod means the image predates that change. |
| **`add-gke-clusters` registers a cluster but `kubernetes_*` calls fail to authenticate** | The auth plugin is resolving different credentials than OpenSRE. Point `GOOGLE_APPLICATION_CREDENTIALS` at the same service-account key, or run `gcloud auth application-default login`. |
| **`add-gke-clusters` reports "no endpoint or CA certificate"** | The principal can list clusters but not read their master config. Add `roles/container.clusterViewer`. |
| **A Cloud Run deploy "succeeded" but nothing changed** | The new revision never became ready, so the old one still serves every request. `gcp_list_cloud_run_services` flags this as `rollout_pending`; the reason is in `failing_conditions`. |
| **A Cloud SQL instance is `RUNNABLE` but refuses writes** | Either it is out of disk — check `disk_pressure` and `out_of_disk_state` — or you are connected to a read replica, in which case `accepts_writes` is `false` and `replica_of` names the primary. |
| **Every subscription reports `backlog_unknown`** | The principal has `roles/pubsub.viewer` but not `roles/monitoring.viewer`. The backlog metrics live in Cloud Monitoring, not in the Pub/Sub API. |
| **A Pub/Sub backlog never drains** | Check `dead_letter_topic`. An empty value means a poison message is retried forever. For a `push` subscription, the failing consumer is the endpoint in `push_endpoint`, not a worker you can inspect. |
| **`gcp_error_reporting_top_errors` returns nothing during a real incident** | Error Reporting only clusters exceptions that reach it. A service logging errors as plain text without a stack trace never appears. Use `gcp_logging_query` with `severity=ERROR`. |
| **`partial_errors` on a multi-project listing** | One project denied the call while others answered; the results you got are real. The message names the project and the missing permission — usually one of the per-service viewer roles in [Prerequisites](#prerequisites). |
| **`unreachable_locations` / `unreachable_scopes` in a result** | Google could not reach a zone, so the listing is incomplete. Re-run; if it persists, check the [GCP status dashboard](https://status.cloud.google.com/). |

## Security best practices

- Grant only the viewer roles you need. `roles/logging.viewer` and `roles/monitoring.viewer` are the baseline; everything else is per-service and listed in [Prerequisites](#prerequisites). The integration is read-only and never writes to your projects.
- No tool reads your data. Cloud SQL reports the instance, never its rows; Pub/Sub reports queue depth, never message payloads. The one place application content can surface is the representative stack trace in `gcp_error_reporting_top_errors`, which carries whatever your exception messages carry.
- Kubeconfigs written by `add-gke-clusters` contain no secret — endpoint, public CA certificate, and a delegation to `gke-gcloud-auth-plugin`. Tokens are minted per connection and never stored.
- Prefer **Workload Identity** or **impersonation** over service-account keys — neither creates a long-lived credential to rotate.
- If you must use a key, mount it as a file and point `GCP_SERVICE_ACCOUNT_KEY` at the path rather than putting the JSON in an env var.
- Scope the viewer role at the project level unless you genuinely want the whole folder readable; `GCP_ADDITIONAL_PROJECTS` decides what OpenSRE queries, but IAM decides what it *could*.
